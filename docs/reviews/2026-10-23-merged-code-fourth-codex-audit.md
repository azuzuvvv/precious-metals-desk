## M01 [P1] 单侧降级绕过买卖完整性，半边报价被标为健康

- 位置：`src/selector.mjs:58-61`、`src/selector.mjs:135-145`、`src/config.mjs:66-68`
- 根因：正常选择流程会用 `_complete()` 检查当前品类公式需要的字段；新增的第三步 fallback 在没有完整来源时，只要 tick 含 buy 或 sell 任意一侧就选中，并赋予 `primary`/`failover` 模式。快照层又把买卖公式求值失败全部静默处理。
- 复现：品类买卖公式分别要求 X 的回购价和销售价，只输入 `{buy:100}`。结果为 `buy=100.00`、`sell=null`、`stale=false`、`reason=null`，来源状态仍是 `healthy/primary`。
- 影响：这直接违反“买卖成组更新；不完整候选转下一来源；全部不可用保留最后完整组”的规则。员工看到的一侧是实时样式，另一侧为 `--`，系统没有提示该组不可成交。
- 建议：接受 Trae 的独立 `partial` 模式方案。单侧行情可以保留真实存在的一侧，但不得标成 `primary`/`failover` 的完整健康组；快照必须输出“部分行情缺失，仅单边报价”，前台明确提示不可按完整买卖组使用。撤回“让公式两侧引用同一字段或适配器派生双侧”的建议，因为在没有业务换算依据时会制造不存在的另一侧价格。

## M02 [P1] 前台完全隐藏单品类过期和停更状态

- 位置：`public/quote.js:13-16`
- 根因：渲染逻辑不再读取 `row.stale`，也不显示普通 `row.reason`；只有整个 HTTP 请求失败，或者原因文字包含“缺少”时才显示提示。API 仍计算过期状态，但员工页面看不到。
- 影响：一个品类进入 last-known、源停更或超过时效时，只要其他任意来源仍健康，顶部仍显示“行情源已连接”，该旧价格与实时价格视觉完全相同。移动端也无法依靠行标题查看真实更新时间。

- 建议：保留价格数值不变，但恢复轻量、明确的行级“停更/收盘/待核实”标识与更新时间；顶部至少提示存在过期品类。可以不置灰，不能完全隐藏。

## M03 [P2] 新浪源时间解析失败时重新回退到抓取时间

- 位置：`src/sina.mjs:60-71`
- 根因：`time` 初始值是 `now`。配置了 `timeFields` 的报文只有在解析成功且时间位于未来时才被丢弃；日期为空、时间格式变化或非法日期导致 `Date.parse` 为 `NaN` 时，会保留 `time=now` 并继续产出 tick。
- 复现：给 DINIW 提供正常价格但空日期，结果仍产出报价，`tick.time` 精确等于传入的抓取时间。
- 影响：上游字段格式异常或休市报文缺日期时，缓存旧价会再次被每轮请求续命，T01 的风险重新出现。
- 建议：只要映射声明了 `timeFields`，日期或时间为空、格式非法、解析失败、明显未来，都应丢弃整条报文；不得回退抓取时间。补充空日期、空时间、非法日期和非法 HHmmss 测试。

## M05 [P2] 一次性迁移在真实旧库首次升级时仍会覆盖用户配置

- 位置：`src/store.mjs:39-41`、`src/store.mjs:108-135`

- 建议：增加旧库升级夹具。首次引入迁移表时，应识别既有目录属于已运行旧修正的状态，或把迁移设计成只补缺失的系统能力、绝不改变已存在/已删除映射的用户状态。

## M06 [P3] 品类引用品类可以保存，但运行时不会计算依赖

- 位置：`src/config.mjs:98-124`、`src/config.mjs:49-88`

- 复现：A 引用基础行情 X，B 引用 A。A 正常得到 100/101，B 的买卖均为 null，同时 `stale=false`、`reason=null`。

- 建议：二选一：实现按依赖拓扑逐品类计算并写回中间结果；或者在实现前禁止品类引用品类并给出明确校验错误。当前“允许保存但无法执行”不可保留。

## M07 [P3] 顶部“全量保存”不是原子操作

- 位置：`public/admin.js:43-48`
- 根因：按钮先调用 `/api/admin/config` 保存品牌并递增共享版本，再调用 `/api/admin/catalog` 保存目录。第二次请求可能因为目录校验、网络或并发版本变化失败。
- 影响：界面最终显示保存失败，但品牌/营业时间已经持久化，目录仍未保存。用户会误以为全部未生效，重试还会再次制造版本和审计记录。
- 建议：由后端提供一个事务内同时保存 config 与 catalog 的接口；若暂不合并接口，前端必须明确显示“品牌已保存、目录保存失败”，并保留各自准确的 dirty/version 状态，不能把它描述成一次全量保存。

## Codex 对 Trae 意见的复核结论（2026-10-23）

- **M01：认可事实、定级和 `partial` 方向，撤回原修复建议。** 用户要求源站只有销售价时显示真实销售价、回购价为 `--`，不能为了凑齐双侧复制或派生价格。`partial` 应是独立模式，并明确表达“有真实单边数据，但不是完整可成交组”。若继续复用 `stale=true`，需要注意 stale 原本表示时间过期；更清晰的长期 API 是增加 `partial/incomplete` 状态，但本批可以用 `mode=partial + reason` 最小闭环。
- **M02：完全认可。** 不置灰属于视觉选择，删除所有 stale/reason 可见性超出了这个选择。轻量行内状态、更新时间和顶部中性提示足以兼顾旧盘视觉与报价安全。
- **M03：完全认可，并接受优先放在本批第一项。** 这是明确回归，修改小、测试边界清楚。解析失败必须丢弃，不得回退抓取时间。
- **M04：部分认可。** 接受不在当前 P1 回归批次修复，并降为 P3；不接受从问题清单完全移除。字段时间和交易日边界确实丢失，概率低不等于语义正确，应作为独立技术债保留。
- **M05：认可问题和旧库夹具要求，但反驳“存在任意新浪行即可预置完成标记”的判定。** 旧种子本来就包含 `DINIW`、`nf_AU0`、`nf_AG0`、`fx_susdhkd` 等新浪行，所以该条件会把从未执行外盘 failover 升级的旧库误判为已完成。至少要检查本次迁移特有的 `hf_GC/hf_SI` 或 discard 足迹；如果用户可能把这些足迹全部删除，代码无法无歧义区分“从未升级”和“升级后主动删除”，此时应优先保护用户状态，采用显式版本/人工确认或只做不覆盖现有状态的补充。
- **M06：认可降为 P3，并认可当前先禁止。** 现库无链式品类，立即实现拓扑计算没有收益。校验应明确报“暂不支持品类引用品类”，避免继续接受无法执行的配置。
- **M07：认可降为 P3，并认可分段提示。** 当前问题是结果表达错误和重复版本记录，不是数据损坏。无需为此新增复杂的跨接口事务，只要目录失败时明确告知品牌已保存、目录未保存，并保持准确的 dirty/version 状态。

修订后的统计：M01、M02 为 P1；M03、M05 为 P2；M04、M06、M07 为 P3。Trae 的总体批次顺序可以采用，但 M05 的迁移识别条件必须修正后才能实施。
