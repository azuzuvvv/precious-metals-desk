# 行情访问保护一期：首版代码审查（Codex，2026-10-28）

结论：暂不发布。本轮确认一个直接导致持续看盘失效的 P1，以及四项 P2。仅审查与复现，不修改业务代码或线上配置。基线为保护方案第 15 节 + 16.3 + 17 节。

## AP-01 [P1] 首轮轮询后 polling 永远为 true，页面不再更新

位置：public/quote.js:52–68。

runPoll 入口将 polling=true，但成功、429、异常分支均没有恢复 false。下一轮 setTimeout 执行时直接在入口 return；online/visibilitychange 的 nudge 同样因 polling 为 true 失效。因此正常页面只拿一次行情，首次请求失败也不能自动恢复，直接违背持续挂盘要求。成功后 failed=false，冻结的报价还可能持续呈现为正常。

已用实际前端轮询代码与 VM 的假 fetch/定时器复现：首次完成为 fetches=2（初始化+行情）、timers=1、polling=true；执行下一轮定时器后 fetches 仍为 2、timers=0、polling=true。

建议使用统一 finally 释放请求标记，所有分支统一安排下一轮，确保无重叠且成功、401、429、网络异常之后都能继续。新增前端流程测试，至少执行三轮，不能只断言首次渲染。

## AP-02 [P2] 会话初始化的限流响应丢失，恢复事件也可能提前重试

位置：public/quote.js:41–49、63–70、75。

ensureSession 遇到非 2xx 只抛空 Error，丢弃状态码和 Retry-After。401 后会话发放若返回 429 且要求等待 60 秒，外层只走通用 2/4/8/16/30 秒退避，会提前继续发起会话创建。首次初始化的失败还被 catch 忽略，紧接着请求行情并可能再次创建会话。

另外，nudge 不检查服务端最早重试时间；修复 AP-01 后，用户切换标签/恢复网络可能提前打断 429 的等待。当前仅行情 GET 的直接 429 分支保留 Retry-After，不覆盖整个恢复流程。

建议为初始化和行情使用统一的状态/退避错误，保留服务器最早允许重试时间；首次启动和恢复事件都遵守该期限。回归用例应覆盖初始化 429、401→初始化 429、等待中切换可见性、到期后正常恢复。

## AP-03 [P2] 失效后的新请求仍加入旧代次在途快照

位置：src/snapshot-cache.mjs:18–27。

invalidate 仅清空 buffer 并增加 generation，旧 inflight 仍保留。配置保存失效之后到达的新 get() 直接返回该旧 Promise，仍可收到保存前的配置/价格公式。代次检查只阻止旧值回填，没阻止新请求读取旧在途结果，与注释“旧结果只发给已等待的请求”不一致。

独立复核复现：挂起构建 old → invalidate → 发起第二次 get → 放行 old；结果 before=old、afterInvalidate=old、builds=1。现有测试只在旧任务完成后发起第二次 get，遗漏了这个窗口。

建议记录在途任务代次；失效后新请求等待旧任务结束再共享新代次重建，保持单笔构建在途。回归同时断言失效前等待者允许获得 old、失效后新等待者必须获得 new，旧结果不能回填。

## AP-04 [P2] 限流状态容量满时，对所有未记录 key 无限放行

位置：src/rate-limit.mjs:19–20。

maxKeys 满且清扫不能释放时，check 直接返回 ok=true，不记录新 key，也没有上层容量溢出计数。持续占满活跃桶后，未记录 IP 的行情/IP 发放限制失效；observe 也无法识别这些本应受限的访问。这一行为在异常负载下撤掉保护，不符合有界容量下仍需受控的目标。

纯单元复现：maxKeys=1，先填入 a；b 连续三次 check 全部 ok=true，即使 perMinute=1、burst=1 且时间没有前进。默认线上阈值为 20000，本轮没有对生产发起填满测试。

建议饱和时使用有界溢出桶或可重试拒绝，并明确记录指标；保留已存在正常桶的独立判定，不以无界扩容解决。添加容量饱和及恢复测试。

## AP-05 [P2] 待部署 Nginx 示例把行情策略套到了整个站点

位置：服务器部署与运维.md:255–271。

gzip 和待启用的 limit_req 都放在 location /。照示例开启 enforce 后，页面资源、后台、会话发放也进入行情 IP 桶，不再是方案限定的公开行情路由。达到行情 IP 限额时，后台或会话恢复可能一起被挡。gzip_types application/json 也覆盖所有该 location 的后台 JSON，不符合仅公开行情压缩的范围。

示例还没有显式约定 limit_req_status；Nginx 常规默认拒绝为 503，与设计中的 429/Retry-After 契约不一致。此项为待部署配置缺陷，本轮没有实际修改或验证生产 Nginx。

建议将 gzip/行情 limit_req 限定到精确 /api/quotes location，完整保留其代理头配置；后台、静态资源、会话发放不共享该桶。明确代理返回 429 及合理重试提示，或在文档明确前端如何兼容代理级 503，不能将 Node 429 测试当作 Nginx 验收。

## 额外边界观察

- 限流器 size 使用 Map.length，实际返回 undefined；应为 Map.size。当前不影响主请求路径，但会妨碍容量观测。

### AP-02 残留 [P2] 首次会话创建的限流响应仍被忽略

位置：public/quote.js 文件末尾 `ensureSession().catch(()=>{}).finally(()=>runPoll())`（当前约第 95 行，以该表达式定位）。

ensureSession 已能把 Retry-After 传播为错误，但页面启动处直接吞掉该错误并立即 runPoll。若首次创建返回 429、Retry-After:60，紧接着行情 GET 返回 401，就立即再次 POST 创建会话；第二次创建失败后才开始遵守 60 秒等待。若首次失败后的 GET 在 observe 模式成功，则首次限流信息完全被忽略。

实际轮询代码 VM 复现：所有会话 POST 返回 429/60 秒，行情 GET 返回 401，初始化完成后的调用顺序为 `["/api/viewer/session","/api/quotes","/api/viewer/session"]`，三次均立即发起，最后才登记约 60 秒定时器。多设备恢复或发放接口繁忙时会额外放大初始化请求。

建议启动阶段也走同一套错误处理与调度逻辑：失败时先设置 earliestRetryAt、提示和退避，期限前不发起恢复请求；不要用空 catch 忽略首次失败。新增“首次初始化即 429”的前端回归，并断言期限前没有行情/第二次创建请求、期限后能恢复。
