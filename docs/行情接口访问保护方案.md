# 行情接口访问保护方案（待确认）

> 2026-10-28 补充：第 13 节为 Trae（Claude）撰写的评审修订，输入与结论已与需求方确认，与正文共同构成当前设计结论；正文其余部分保持 codex 原稿。

## 1. 目标与边界

正常访客打开页面即可看实时行情，不要求注册登录。家里电脑允许全天、连续多天挂盘，后台标签页不因缺少鼠标操作而失效；断网、休眠、服务重启后自动恢复。保护当前行情服务，限制直接调用及高频批量采集，同时为其他业务后台提供独立的受控入口。

F12 的 Network 请求无法隐藏。改名、Base64、JavaScript 混淆、切换 WebSocket 都不能让浏览器已经收到的数据变成秘密。此方案提高直接盗用和批量采集的成本，不承诺阻止正常速度、完整模拟浏览器的采集程序。

重要更正：之前“直接复制接口一定拒绝”的描述需要限定为没有有效凭据的请求。同一浏览器直接打开接口、复制包含 Cookie 的完整请求，仍可能成功；公开会话发放入口也能被程序模拟。匿名凭据提供的是会话管理和限额基础，不是对真人的可靠鉴别。

如果将来需要只有指定人可获取实时行情，必须另选访问密码、邀请或账号授权模式；它与本次“任何正常访客都能直接看”的目标不同。

## 2. 三种选择

| 方案 | 正常使用体验 | 能力与代价 |
| --- | --- | --- |
| A：仅 Nginx 限流 | 无感，挂盘方便 | 最简单，降低高频请求压力，接口仍可直接调用 |
| B：匿名会话 + 两层限流 + 服务端独立密钥（推荐） | 无需登录，自动恢复 | 限制无会话调用和单会话滥用，可监测撤销；浏览器模拟仍可绕过匿名发放 |
| C：授权看盘 + 必要时异常验证 | 首次或异常时需要操作 | 控制谁有资格获取实时行情更有效，但增加家庭设备及其他访客操作成本 |

推荐先实施 B。不要一开始引入复杂指纹、验证码、付费 WAF 或新增 Redis。后续是否升级 C，由实际滥用与误拦截记录决定。

## 3. 现状与改动范围

- 当前前台每次请求结束后约 2 秒再次获取 GET /api/quotes，正常单标签页约每分钟 30 次。
- 该接口公开、无访客鉴权；Host 校验用于限定入口，不能鉴别采集者。
- 管理后台已经有登录会话和 CSRF 校验，继续独立使用，不能拿管理员会话给看盘页复用。
- 服务器：Nginx 3189 → 127.0.0.1:3188，systemd 单 Node 进程，MySQL 5.7。其他 Nginx 服务保持原配置。
- 当前 HTTP 临时入口可以验证流程，但 Cookie/API Key 的传输机密性必须在 HTTPS 上成立。备案后接入免费证书；正式公网开放跨服务密钥以前完成 HTTPS。

## 4. 网页访客会话

### 4.1 请求流程

1. 页面正常加载，不在页面源码或脚本中嵌入长期密钥。
2. 页面调用同源 POST /api/viewer/session，服务端发放随机不可预测的匿名会话 Cookie。接口返回过期策略等非敏感元数据，不返回 Cookie 明文。
3. GET /api/quotes 必须携带有效访客 Cookie，并通过会话/IP 限流，才返回行情。接口返回 Cache-Control: no-store。
4. 无效或过期会话返回 401，前台只发起一次会话重建，再重试行情。不得无限立即循环。
5. 正常请求延长会话空闲有效期；标签页开着持续看盘无需手动重新验证。

Cookie 与管理员登录 Cookie 分开命名；使用 HttpOnly、SameSite=Strict、Path=/，不设置 Domain。HTTPS 正式入口设置 Secure；临时 HTTP 入口必须显式配置兼容模式，不能自动相信外部请求声明的协议。

建议采用内存随机会话，无需 JWT、无需每两秒查数据库：32 字节安全随机标识，空闲超时 30 分钟，浏览器 Cookie 最长保存 7 天。成功行情访问刷新服务端空闲期限；Cookie 剩余不足一天时续写。不能把 7 天当作需要手工重新登录的期限，过期或进程重启由页面自动重建。

后台标签页被浏览器暂停或机器休眠后，恢复时可能已超过 30 分钟；自动重建是正常路径，不算异常、不能因此封 IP。匿名会话不能访问 /api/admin/*。

### 4.2 发放入口的边界

发放前校验精确 Origin、JSON 类型，存在 Fetch Metadata 时拒绝明显跨站请求；这些只作为跨站滥用防护，不能作为真人证明。后端程序可以伪造这些头。

有效 Cookie 的重复初始化应幂等复用会话，不生成无数新会话。无效 Cookie 或新浏览器受发放频率限制。过期会话定时清理，建议全局最多保留 10000 个活跃会话，并对 IP 桶等状态也设置有界容量和淘汰策略；容量不足返回可重试错误，不驱逐正在正常看盘的会话。

暂不强绑定完整 IP 或 User-Agent。家庭宽带、手机网络变化不应导致频繁失效；IP 作为限流和异常观察维度。也不依赖鼠标、键盘、页面焦点证明真人，家里无人操作持续挂盘应保持正常。

## 5. 限流策略（初始参数，需根据观察调整）

| 范围 | 持续速率 | 突发余量 | 超限处理 |
| --- | --- | --- | --- |
| 每个访客会话的行情请求 | 每分钟 120 次 | 额外 30 次 | 429，返回 Retry-After |
| 每个公网 IP 的行情请求合计 | 每分钟 600 次 | 额外 120 次 | 429，短暂退避 |
| 每个 IP 新建访客会话 | 每分钟 30 个 | 额外 10 个 | 429，不自动永久封禁 |

以上是令牌桶/等效平滑限流的初始建议，不是已上线配置。正常单标签页约 30 次/分钟；同浏览器共享 Cookie 的 3–4 个标签页以及家庭多设备需实测。长时间访问本身不是滥用，不设置每天看盘时长或累计请求次数上限。

Node 根据访客会话限制速率，Nginx 对本项目公开入口做 IP 粗限流。Nginx 只对本项目相应 location 生效；limit_req_zone 等定义放入 http 作用域允许的位置，先检查现有版本/模块，再 nginx -t 后 reload。不能把粗限流直接套到整个服务器、静态资源、管理员或其他业务上。

初期仅记录异常和返回 429，不因一次超限永久封 IP，也不因不动鼠标或固定 2 秒轮询判机器人。只有持续高频、频繁生成会话等明确滥用行为，才考虑 5 分钟等短期阻断；默认先限会话，谨慎处理共用出口 IP。

Node 不直接使用外部传入 X-Forwarded-For 的首项作为真实 IP。只有受信任的本机 Nginx 可以提供客户端地址；本方案选择由 Nginx 覆写专用客户端 IP 头，Node 仅在连接来自本机且启用代理信任配置时使用该头。本机其他进程属于受信任服务器边界。未来加 CDN 时重新定义可信代理链。

## 6. 长时间挂盘与故障体验

- 保持正常 2 秒轮询；前一请求结束后安排下一轮，禁止请求重叠。
- 一处统一管理会话重建任务，多个失败不能同时触发大量初始化。
- 401：自动重建会话并重试一次；反复失败时退避，不刷新整个页面。
- 429：遵守 Retry-After，增加小幅随机退避，不持续两秒轰炸；服务端已拒绝时保留旧报价并显示访问暂受限制。
- 断网/5xx：按 2、4、8、16、30 秒上限退避，恢复后回到正常频率。此前保留的价格必须明确标记停更，不能冒充实时。
- sleep/resume、online、visibilitychange 只触发去重后的恢复检查；隐藏标签页仍可看盘，不强制登出。浏览器自身节流意味着休眠期间无法承诺实时刷新，恢复后立即重新获取。
- 观测模式下不强制鉴权；强制模式开关由服务端配置。前端先具备会话/退避兼容，再开启后端强制策略，避免旧浏览器页面瞬间失效且无法恢复。

不建议首期切换 WebSocket/SSE。它们可改变传输方式，但不是防爬核心；先保留当前轮询，减小影响行情业务的改动范围。

## 7. 其他后台服务的接口

建议新增 GET /api/service/quotes，复用报价快照业务，独立执行后台鉴权，不走匿名网页 Cookie。

- 每个消费服务一把可撤销的高熵 API Key，通过 Authorization: Bearer 请求头携带，不放 URL，不放前端 JavaScript。
- 数据库只存 Key 的哈希、编号、名称、启停状态及限额。首期通过服务器管理脚本生成/撤销，不扩展后台管理界面；明文仅生成时显示一次，不能记日志。
- 首期只读报价权限，不开放后台配置或供应商 Token。默认返回现有展示报价；原始行情需求另行确认，避免把后台公式价与原始价格混淆。
- 每 Key 默认每分钟 120 次、突发 30 次，IP 粗限流需为该接口独立设置，不能把它当作无凭据公开接口开放。
- 同机服务用本机地址及正确 Host 调用，仍带 API Key；不同服务器通过 HTTPS。IP 白名单只是补充，不代替 Key。
- 支持新旧 Key 短暂重叠后撤销旧 Key，服务之间不共用 Key。

这部分可作为第二批改造；第一批网页防滥用上线时先盘点是否已有后台调用旧接口，不能未迁移就突然强制 Cookie。

## 8. 可观测性与模块划分

建议新增独立模块 src/viewer-session.mjs、src/rate-limit.mjs；如实施后台接口，再新增 src/service-auth.mjs。src/server.mjs 只负责路由装配，不混入大段限流状态处理；src/quotes.mjs、选源与公式计算逻辑保持原职责。

public/quote.js 增加会话恢复与退避；src/store.mjs 只在后台 Key 阶段增加持久化记录。单进程会话与限流状态放内存；将来多实例时才评估共享存储，不能把单机实现误用于多进程全局配额。

记录时间、路由、拒绝原因、状态码及必要的聚合计数。不记录 Cookie、Authorization、完整 Token 或全部请求头；需要关联会话时使用不可还原的短摘要。禁止在日志中复制带凭据的 URL。IP 日志设置保留期与轮转，避免占满旧服务器磁盘。

首期用状态码与聚合日志观察，不新增管理大屏。区分 401 无会话、429 超限、真实行情缺失，避免把访问控制故障误判成供应商断线。

## 9. 验收标准

1. 无需登录首次打开页面可显示行情；无 Cookie 直接请求 /api/quotes 在强制模式返回 401。
2. 同浏览器带有效 Cookie 可成功读取，明确证明不是“F12 看不到/复制绝对无效”的伪目标。
3. 连续挂盘 72 小时不要求人工续期；先用可控时钟验证生命周期，再做真实时长验收。
4. 同浏览器四标签页、同 IP 多设备正常访问；没有因为固定轮询、后台标签或零交互而误封。
5. 会话到期、服务重启、断网和休眠恢复后自动重建；初始化和行情请求均无并发风暴。
6. 会话/IP/发放三种限流分别命中，正确返回 429、Retry-After，等待后恢复。
7. 验证伪造 X-Forwarded-For 不能改变实际限流主体；会话与限流记录容量有界。
8. 凭据错误/超限时旧价格明确停更；源数据 stale 等既有业务语义不被覆盖。
9. 匿名看盘会话不能访问后台；后台接口拒绝缺少、错误、撤销的 Key，两个 Key 配额独立。
10. 线上域名 HTTPS、Cookie 属性、日志脱敏、其他 Nginx 服务不受影响均验收通过。

## 10. 上线顺序与回退

1. 先确认本设计及现有后台调用情况，不操作线上。
2. 第一批实现访客会话、前端自恢复、两层限流、测试与日志；默认观测模式。
3. 验证 Nginx 版本、模块和真实 IP 链；备份代码及配置，更新前端兼容逻辑，观察旧页面使用情况。
4. 先开启温和限流，检查家庭多开、长时间运行和误拦截，再开启无会话拒绝。旧版已加载页面可能需要一次刷新，应提前说明，不能声称旧客户端也会自动恢复。
5. 备案完成后接入 HTTPS，开启 Secure Cookie；再启用公网后台 Key 接口。HTTP 原入口不能绕过正式 HTTPS 保护。
6. 第二批按需要增加后台 Key 接口，迁移已有服务调用。
7. 如误拦截，先回到观测模式、调整限流；必要时恢复原 Nginx/代码。数据源配置、数据库报价及供应商密钥不因本改造被重置。

## 11. 不纳入首期

不禁用 F12，不拦鼠标右键，不做自定义加密报价、不内置长期共享 Token、不以隐藏路径/Referer/CORS 作为核心鉴权。不做完整浏览器指纹、自动永久 IP 封禁、强制验证码和购买云防护产品。

若低频模拟浏览器采集仍无法接受，应改为 C：受邀用户登录/设备授权，或将公开页面改为延迟报价、授权用户获取实时数据。该升级影响业务可见范围，须另行确认，不在本次默认方案中偷偷加入。

## 13. 评审修订（Trae / Claude 撰写，2026-10-28）

本节由 Trae（Claude）撰写，以下输入已与需求方确认，结论据此定稿；上文第 1–12 节为 codex 原稿，未改动。

**确认的输入**

- 预期同时挂盘的浏览器可达几十个；形态两种都有——多设备各自独立浏览器（独立 Cookie、独立会话）与同一浏览器多标签页（共享 Cookie、计入同一会话）并存；
- 设备分散在不同网络（各自独立公网 IP），非同一宽带集中出口；
- 服务器公网带宽 3 Mbps，与同机其他 Nginx 服务共享出口；
- 对推送升级的动机：容量担忧与产品体验两者都有。

### 13.1 现有问题：管理后台限流在 Nginx 后退化为全局共享桶（并入第一批）

src/server.mjs 的 rateLimit() 以 req.socket.remoteAddress 为键，而线上流量经 Nginx 反代（3189 → 127.0.0.1:3188）后该值恒为 127.0.0.1：全部访客共享同一个"12 次/分钟"桶，陌生人刷登录接口即可锁死管理员登录。第 5 节的可信代理 + 专用客户端 IP 头设计应提前到第一批实施，并把现有 admin rateLimit() 一并迁移到该取 IP 逻辑，而非只服务新的访客限流。

### 13.2 限流参数修订

每标签页 2 秒轮询 ≈ 30 次/分钟。同浏览器多标签页共享 Cookie、全部计入同一会话；多设备各自独立会话（各约 30 次/分，远低于会话上限）。据此修订：

| 范围 | 原稿初值 | 修订值 | 依据 |
| --- | --- | --- | --- |
| 每会话行情请求 | 120/分 + 突发 30 | 180/分 + 突发 30 | 覆盖同浏览器 6 标签页（原 120 仅够 4 页贴边，抖动即 429） |
| 每 IP 行情合计 | 600/分 + 突发 120 | 维持 | 设备分散不同网络，单 IP 正常负载远低于此 |
| 每 IP 新建会话 | 30/分 + 突发 10 | 维持 | 分散网络下，服务重启后的集中重建也宽裕 |

三个限流值全部做成配置项（环境变量或配置表）：若将来出现"单店铺几十块屏集中一条宽带"的客户，只改配置不改代码。

### 13.3 服务端必做：快照缓存 + 预序列化共享 buffer

/api/quotes 当前每请求执行 catalogSnapshot()（MySQL 取连接 + 开事务）。几十台挂盘 ≈ 每秒 10–20 次数据库事务往返，不可持续。修订：

- 进程内 1 秒 TTL 快照缓存，与 publish 定时器（1 秒）对齐；后台保存目录时主动失效，数据库压力归到每秒 1 次；
- publish 时对快照 JSON.stringify 一次，所有连接共享同一预序列化 buffer（gzip 结果亦可每秒只压一次），单请求成本降为"Map 查询 + 发 buffer"，微秒级。

该缓存与限流互补：限流是"减速"，缓存是"减重"，两者都上一期才成立。

### 13.4 带宽约束（3 Mbps）：gzip 升级为一期必做

出口 3 Mbps ≈ 375 KB/s 且与其他服务共享；行情流量按 60% 预算（≈1.8 Mbps）规划。按快照 5KB/次估算（以实测为准）：

| 并发浏览器 | 轮询 2s 裸流量 | 轮询 + Nginx gzip（约省 70%） |
| --- | --- | --- |
| 40 台 | 0.8 Mbps（占管道 27%） | ~0.25 Mbps |
| 100 台 | 2 Mbps（67%，挤占其他服务） | ~0.6 Mbps |
| 200 台 | 4 Mbps（超出管道） | ~1.2 Mbps |

- Nginx 对本项目相应 location 开启 gzip，一期必做（JSON 重复字段名压缩率高）；
- 每 IP 限流 600 次/分的副产品价值：单个滥用 IP 最多占管道约 13%，限流即带宽保险；
- 经济账备注：若未来达数百块店铺大屏规模，升带宽（按量付费 / 5–10 Mbps）可能比开发增量编码更便宜，触发时先算账再动工；
- Nginx access log 将达每天百万行量级，确认 logrotate 覆盖本站点；
- 验收补充：目标并发下行情出口峰值 < 60% × 3 Mbps；观测期记录快照字节数与请求速率。

### 13.5 推送升级决策：SSE 替代 WebSocket，触发式二期

本项目中 WS 由 SSE 取代，理由：行情推送是纯单向场景；EventSource 浏览器自带断线重连；握手即普通 GET，访客 Cookie 鉴权直接复用；Nginx 无需 Upgrade / proxy_http_version 配置。WS 需额外承担握手鉴权、心跳清死连接、客户端手动重连、双路径回退与专项测试，均为纯成本。第 6 节"不建议首期切换"维持不变。

同样载荷下，1 秒推送一次比 2 秒轮询一次流量翻倍：push 省的是连接与 HTTP 头开销，省不了数据本身。故二期推送必须搭配增量编码（增量 + gzip 预估 200 台 ≈ 1 Mbps）。

量化触发线（满足其一即启动二期）：

1. 持续并发 > 100 台浏览器；
2. 行情出口流量峰值 > 1.8 Mbps；
3. 产品明确要求亚秒级更新；
4. 出现集中大屏客户（先按 13.4 算带宽账）。

push 落地后限流语义更干净：由"请求速率限流"改为"每会话/每 IP 连接数限流"，且服务端定速推送、客户端无法加速拉取，天然抑制批量采集。前端可选优化：BroadcastChannel 让单标签页轮询、广播给其余标签，N 标签请求量降为 1 份，并可顺带根治 4.1/6 节的跨标签页 401 会话重建竞争（各标签各自重建会产生少量孤儿会话，量小有界，不实施亦可接受，但需知情）。

### 13.6 盘点与观测补充

- 第 7 节盘点清单加入自有脚本：scripts/verify-live.mjs、scripts/qa-server.mjs 直打 /api/quotes，强制模式下将被 401，需改走会话或服务 Key；另盘点可能存在的外部拨测/uptime 探测；
- 观测模式除状态码聚合外，单独统计"若强制模式开启会被拒"的计数（无会话命中、超限命中分开），作为切换强制模式的量化决策依据；
- 第 10 节第一批交付物相应增加：可信 IP 头迁移（13.1）、限流参数配置化（13.2）、快照缓存与预序列化（13.3）、Nginx gzip（13.4）。

## 14. Codex 对 Trae 补充的独立评审（2026-10-28）

本节明确标注为 Codex 的认同、反驳及补充，不修改 Trae 原文，不表示实施已获批准。采用 receiving-code-review 的核实方式：先对照代码与官方文档，再下结论。本轮只修改方案文档。

### 14.1 总体意见

认同真实 IP 修复、限流配置化、减少重复快照计算、行情 JSON 压缩、上线前观测和脚本盘点；不同意把未测量的容量判断当事实，也不同意把 SSE 描述成天然防采集或无需处理连接生命周期。二期优先评估 SSE 合理，直接宣布它替代 WebSocket、强制增量编码则过早。

Trae 记载“几十浏览器、网络分散、六标签页”等已确认输入，本轮不重新要求用户确认；但这些是规划输入，不能当成已测出的线上并发、共享出口比例或快照尺寸。

### 14.2 认同 13.1：管理员限流确有代理 IP 问题

实际 `src/server.mjs:121` 使用 req.socket.remoteAddress；当前 Nginx 通过本机转发，因此公网访客通常被计入同一个本机地址桶。登录、初始化、改密共用该限流器，外部刷登录确实可能连带阻止正常管理操作。这不是推测，应并入第一批修复。

“锁死”应理解为限流窗口内拒绝，当前窗口为一分钟，不是永久锁定。迁移真实 IP 时必须沿用可信代理边界；同时验收外部伪造 IP 头不能换桶。仅修复按 IP 统计仍无法完全防止分布式登录攻击，不夸大修复收益。

### 14.3 部分认同 13.2：180/分钟可作为初值，但仍是六页贴边

把参数做成配置项认同。180/分钟可比 120/分钟更宽松，但六页各约 30 次/分钟，仍接近 180 上限；额外突发量只能吸收短期集中，不能为超过持续速率的负载永久补额度。原轮询在请求结束两秒后再发起，真实频率通常略低，也不能直接断言原四页必然因抖动被拦。

建议暂用 180/分钟、突发 30 作为观察初值，若“六页长期稳定”成为硬性验收，应实测后留持续余量，例如调整到 240/分钟，而不是只改突发。调大限额也允许单会话采集更多，需承认这种取舍。

### 14.4 认同缓存方向，反驳 13.3 的容量断言与未完成设计

代码确认 /api/quotes 每次调用 catalogSnapshot，存在重复数据库及公式计算成本，做进程内共享缓存合理。但“每秒 10–20 次事务不可持续”“微秒级”都缺乏本服务器压测依据，应删除保证性措辞。普通本机 MySQL 是否承受得住取决于事务内查询数量、CPU、连接池及并行业务，不能由次数直接断言。

缓存需补齐以下规则，才能纳入第一批：

1. 区分数据库配置快照与最终报价快照；前者减少数据库读取，后者复用公式求值及序列化。可以先使用一个统一快照模块实现，不要求同时维护两套复杂缓存。
2. 只允许一笔重建在途，过期时并发请求复用同一 Promise；否则 TTL 到期时几十请求仍可能同时查询数据库。
3. 配置/目录保存成功都要失效，不只目录；重建前捕获版本或代次，保存后完成的旧重建不得重新放回缓存。预览草稿必须独立计算，不进入公开共享缓存。
4. 鉴权、限流先于读取共享响应；只共享行情 body，不共享 Set-Cookie 等访客响应头。不能用 Nginx 对鉴权接口直接做公共 proxy_cache，从而绕过 Node 检查。
5. 每秒重建或按 TTL 请求时重建选择一种主策略，避免 publish 定时器与请求各自再建一份。纯定时方案无访客时也会耗数据库，应权衡。
6. 无新行情时仍要随时间推进 stale、营业状态和 serverTime，不能只在 tick 变化时刷新；缓存失效/数据库失败的旧响应不能无限当作实时成功返回。第一批不引入无限过期兜底，重建失败返回可重试 503，前台标停更。
7. 1 秒缓存是允许最多约 1 秒复用的设计，不是精确时效保证；时效需要按生成时间验收。若另拆配置 TTL，须说明其更新延迟，不能累加后还声称只延迟 1 秒。

预序列化 Buffer 可以采纳；如果由 Nginx gzip，默认仍按响应压缩，并非“全体访客每秒只压一次”。应用预压缩则要自行处理 Accept-Encoding、Content-Encoding、Vary、Content-Length 和错误分支，首期无 CPU 瓶颈时不增加这层复杂度。

### 14.5 认同 gzip，反驳 13.4 的固定压缩率和“带宽保险”表述

在 3 Mbps 共享出口下，为公开行情 JSON 开启 gzip 是成本较低的合理优化。但 5 KB/次及压缩省 70% 都是估算，不是现有生产报文测量。原带宽表在给定假设下算术基本成立，但不能用它承诺 200 台的容量。

本轮本地使用 defaults.json + 空行情构造实际 snapshot：23 行，原 JSON 7449 字节、gzip 后 935 字节。该夹具尚无真实来源元数据、线上配置及 HTTP/TLS 开销，不是线上容量测试；它只能证明 5 KB 不是一个已经验证的生产常量。应采集线上实际 body 字节数、gzip 比例、请求速率、CPU 和出口带宽，再定并发目标。

600 次/分钟按每次 5 KB 得 0.4 Mbps，约占 3 Mbps 的 13.3%，这个稳态算式正确；但遗漏突发、响应头、其他路由、多 IP/分布式客户端，以及客户端未声明支持 gzip 的情况。它只限制单 IP 单路由稳态请求，不是全站总带宽上限，不能称为可靠带宽保险。不要仅因支持 gzip 就把限额大幅放宽。

gzip 配置只覆盖公开行情等不含秘密的响应，显式包含 application/json，按 Content-Encoding 实测是否生效；不要默认 gzip on 就涵盖 JSON，不扩到后台凭据响应。按 Nginx 官方文档处理 gzip_vary 等协商问题。先由 Nginx 压缩，应用预压缩留给 CPU 数据证明有必要时。

“40 台全天两秒轮询”约 172.8 万次请求/天，日志百万行量级估算成立；若只看营业时段则更少。认同检查 logrotate 和磁盘空间。60% 行情出口预算可作规划目标，但还要观察整机剩余业务峰值与 p95 延迟，不能只验收行情字节数。

### 14.6 SSE 可作二期候选，但反驳 13.5 的四处结论

**一、SSE 不等于不需要 Nginx 适配。** 无需 WebSocket 的 Upgrade 握手属实，但要关闭该流的代理缓冲、安排心跳和 proxy_read_timeout，验证流压缩是否及时 flush，处理慢客户端与断开清理。旧版 Nginx 不应依赖最新默认值；显式评估 upstream HTTP/1.1/连接头配置，不能笼统说无需 proxy_http_version 配置。

**二、自动重连不等于自动恢复鉴权。** EventSource 重连携带 Cookie，但未知/过期会话仍然无效，而且浏览器脚本不能像 fetch 一样直接读取失败响应的 401/429 细节。必须设计关闭重试、用普通请求重建会话、Retry-After 退避。长连接建立后没有轮询刷新空闲时间，原 30 分钟会话续期模型必须调整；服务端要能撤销连接，不能建立一次就永久绕过鉴权。心跳、续期、撤销、连接容量和慢客户端队列边界均有开发与测试成本，不能说这些只有 WS 才有。

**三、SSE 的多标签页约束必须先验证。** HTTP/1.x 下浏览器对同源 SSE 通常有约六连接限制，跨标签页共享。当前 HTTP 临时入口没有已确认的 HTTP/2 支持，恰好存在多标签页需求，所以“更简单”有前提。TLS/HTTP2、单标签共享连接或降低连接数等方案需明确选定，再决定 SSE/WS；BroadcastChannel 本身并不完成选主、租约、主标签休眠/关闭时接管和重复连接处理。

**四、推送不天然阻止采集，增量编码也非必选。** 一个被允许的订阅连接就能持续采集全部推送，减少 HTTP 请求数不等于减少行情泄露；连接数限制控制的是资源使用，仍需会话/Key/重连发放限流。1 秒全量推送相对 2 秒全量轮询会增加 body 频率的判断认同，但还可选择每 2 秒全量、变化才推、只推订阅品种等，不能直接定“必须增量”。增量需要版本号、首次完整快照、删除项、断线补齐或全量重置、慢客户端背压及重新同步，不能只给压缩后的估计容量。

当前源采集不少是 15–30 秒周期；即使浏览器亚秒接收，也不会凭空提高上游数据新鲜度。若产品要求亚秒级行情，必须同时检查供应商更新频率、采集周期和现有 1 秒 publish。

100 并发、1.8 Mbps、集中大屏客户作为“触发容量复评/压测”可以采纳；不赞成任一满足就直接承诺开发 SSE 或增量编码。先定位瓶颈，再比较压缩、缓存、频率调整、带宽及传输方式，成本结论也需届时价格与测量支撑。

### 14.7 认同 13.6，但修正脚本归类

verify-live.mjs 确实直接请求 /api/quotes，需支持新的访问路径；同时核对 Host/PUBLIC_ORIGIN 兼容。

qa-server.mjs 本身是隔离数据库上的测试服务启动器，不是直打 /api/quotes 的调用脚本。其服务的前端或其他验收客户端可能受新策略影响，应盘点这些真正调用方，而不是把启动器改成持有生产服务 Key。测试保持隔离，不拿真实生产凭据跑验收。

认同观测模式分别统计“若强制将拒绝的无会话、超限请求”。只记录实际状态码不够，观测模式下可能全是 200，无法辅助开关决策。

### 14.8 建议采用的修订范围

第一批：可信 IP（覆盖 admin）、参数配置化、访客会话与前端恢复、两层限流及观测日志；增加边界明确的快照缓存/预序列化、公开 JSON 的 Nginx gzip，并通过目标负载测量收益。缓存是性能优化，不把它当防爬鉴权措施。

二期：根据测量评估 SSE/WS、共享标签连接与按需订阅，增量编码独立评估，不默认全做。其他后台 Key 接口继续与浏览器匿名凭据区分。

不改变原方案的核心边界：匿名正常访客能获取的实时数据，完整模拟浏览器的低频采集仍能获取；传输更隐蔽、压缩或推送都不改变这一点。

## 15. 本轮开发基线与交付边界（Codex，2026-10-28）

本节将前述建议收敛成可执行的一期范围，供需求方确认后开发；优先于第 1–14 节的冲突或备选表述。不要求开发者同时实现所有评审建议。

### 15.1 容量与正常访问

- 以 60 个同时打开的看盘页面持续使用为设计目标，100 个页面作容量与退避验证；页面数不等于浏览器/会话数。
- 正常每页面每两秒左右请求，60 页约 30 请求/秒，100 页约 50 请求/秒；带宽、CPU、数据库和延迟需实测，不能直接当作容量承诺。
- 正常场景包括多网络、多设备及同浏览器多标签页；不把无操作、固定周期请求或长时间挂盘视为异常。不引入每日观看次数/时长额度。
- 60 页目标不默认包含 60 页全部共用一个公网 IP。默认 IP 配额按下表；集中宽带场景通过配置和单独验收支持，不能声称任何共享网络规模都不会限流。

### 15.2 一期实现范围

1. 独立匿名访客 Cookie 与会话发放、自动续期；空闲 30 分钟，Cookie 七天并自动续写。无强 IP 绑定，不使用行为验证码。
2. 前端 401 重建、429 退避、断网/休眠/服务重启自动恢复，请求与初始化任务均去重；旧价格保留但不得误标实时，不新增强制弹窗或遮罩。
3. 可信代理客户端 IP 的统一取值，覆盖访客限流与已有管理员限流；访客、管理员计数器独立。
4. Nginx IP 粗限流、Node 会话限流、会话发放限流；参数配置化、计数内存有界、日志脱敏及轮转。
5. 请求触发的进程内报价快照缓存与 JSON 预序列化，TTL 1 秒；一笔重建在途、并发共享 Promise。无访问时无需额外定时读数据库，沿用行情 publish 自己的定时器。
6. 所有影响公开报价的配置/目录提交成功后失效缓存；重建代次保护，旧异步结果不能覆盖新配置；预览不缓存到公开结果。鉴权与限流始终先于命中缓存，Set-Cookie 独立按请求生成。重建失败不无限复用旧报价，返回可退避 503。
7. 仅公开行情 JSON 的 Nginx gzip，显式支持 application/json，协商正确并实测。首期不做应用预 gzip、不把整个站点代理缓存。
8. off / observe / enforce 三种保护模式，初次部署为 observe；同一套判定逻辑生成“会被拒绝”的指标，enforce 才强制拒绝。已存在 Nginx enforce 限流也需单独控制，不能只把 Node 改 observe 却仍被代理拦截。

### 15.3 统一初始参数

| 范围 | 默认持续速率 | 突发余量 | 说明 |
| --- | --- | --- | --- |
| 单访客会话行情 | 240 次/分钟 | 30 次 | 为同浏览器六标签页约 180 次/分钟保留余量，替代上文 120/180 的备选值 |
| 单 IP 行情合计 | 600 次/分钟 | 120 次 | 默认支持十个左右页面共出口并留余量；并非支持六十页同出口的承诺 |
| 单 IP 新会话发放 | 30 个/分钟 | 10 个 | 有效会话幂等复用，恢复失败须退避，不清零行情限额来绕过限制 |

集中出口六十页时可将 IP 行情调整为 2400 次/分钟、突发 240，并将会话发放调整为 90 次/分钟、突发 30 后单独压测。该配置放宽该出口的防滥用能力，只有实际需要时启用；不得默默把所有部署默认提升。所有数量、时长和模式可配置并有合法范围校验。

### 16.1 接受的反驳（已对照代码/脚本核实）

2. **"不可持续"措辞撤回（14.4）**：catalogSnapshot 每次约 4–5 条短查询，每秒 10–20 次调用 ≈ 50–100 查询/秒，在 MySQL 5.7 能力范围内。快照缓存的定位回归"消除每请求连接/事务/公式计算重复成本的优化"，非救命措施；实现规则以 14.4 的七条与 15.2.5/15.2.6 为准（含单航次重建、代次保护、请求触发而非定时轮询）。
3. **13.6 脚本归类更正（14.7）**：qa-server.mjs 实为隔离验收夹具启动器（监听 3210、强制 `lcjy_qa` 前缀库），自身不调用 /api/quotes；真正直打接口的是 verify-live.mjs（127.0.0.1:3188）。盘点口径以 14.7 为准。
4. **六连接限制是 13.5 的真实遗漏（14.6.3）**：HTTP/1.1 下同源 SSE 连接全浏览器共享约 6 条上限，多标签页场景会顶满并饿死普通请求。SSE 的前提从"更简单"修正为"HTTPS + HTTP/2 先行"，与第 3/10 节 HTTPS 里程碑对齐；EventSource 错误事件不暴露 401/429 细节、长连接不刷新会话空闲期等生命周期成本，以 14.6 的口径为准。

### 16.2 一处澄清（非翻案）

13.5"天然抑制批量采集"的本意：push 模式下单连接的请求放大被服务端定速封顶（轮询下单会话最多约 240 次/分，push 下单连接最多收约 30 条/分）。这是资源保护收益，不是数据泄露收益——被允许的连接仍可获取全量推送流。采纳 14.6.4 的表述。

### 16.3 三条补充（并入第 15 节执行）

1. **Nginx→Node 上游 keepalive，并入 15.2.7**：默认配置下 Nginx 对 3188 每请求新建一条 TCP，30–50 req/s 下徒增连接与 TIME_WAIT 开销。增加 `proxy_http_version 1.1` 与 upstream keepalive；该开关即 14.6.1 所指，一期实施则二期 SSE 直接受益。
2. **轮询基础抖动，并入 15.2.2**：在 429 退避随机化之外，2 秒基础轮询间隔增加 ±10–20% 随机抖动，消解服务重启后几十页同时恢复形成的同步轮询波，平滑 p95，亦利于 15.5 压测达标。

## 17. Codex 最终复核：可开工，三条实施细节补齐（2026-10-28）

认同 16.3 三项方向，不再扩大本期范围。以下细节与第 15 节、16.3 合并执行，无需再进行一轮方案讨论。

1. **上游 keepalive 配置必须完整且局部生效。** 仅增加 proxy_http_version 1.1 与 upstream keepalive 不够，应在本项目代理中显式清空 `Connection` 请求头（`proxy_set_header Connection ""`），避免 Nginx 默认传递 close 导致连接不复用；已有 Host、真实 IP 和协议头不能丢失。upstream 名称与现有配置不冲突，限制空闲连接数，nginx -t 后验证连接复用。仅以实际版本及配置判断当前是否每请求新建连接，不能把默认配置推断当作已观测事实。此项是连接优化，不是防爬核心，也不替代 SSE 将来的缓冲/心跳配置。
2. **基础抖动保留“上一请求完成后再调度”。** 可取 2 秒 ±10% 为默认，随机偏移均值为零，单页仍约每分钟 30 次；不使用 setInterval 造成重叠。429 的 Retry-After 是最早重试时间，随机化只能额外延后，不能减去抖动而提前重试。网络失败继续指数退避；恢复事件也必须共用现有去重任务。
3. **脚本初始化必须实现 Cookie 保持。** verify-live.mjs 的 Node fetch 不会像浏览器自动保存并回传会话 Cookie，应显式保留本次服务下发的 Cookie 并在行情请求携带；同时设置匹配 PUBLIC_ORIGIN 的 Host/Origin、JSON 类型并支持配置基础地址，不能硬编码公网旧 IP。脚本不使用管理员会话或真实生产 API Key；失败时不得输出 Cookie 明文。验收脚本正常读取及无会话请求确实被拒绝两个分支。

16.1 的“在 MySQL 5.7 能力范围内”应读作一般量级判断，不是本服务器性能保证；仍以第 15 节测试为准。本地 88% 压缩结果也不替代线上实际报文测量。

结论：设计足以启动本地开发与测试，未发现需要阻断开工的设计问题。开发基线为第 15 节 + 第 16.3 节 + 本节；不直接操作线上、不直接开启 enforce。完成后提交代码与验收结果复审。参考：[Nginx upstream keepalive 官方配置示例](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)。
